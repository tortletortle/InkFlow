# 《墨生》2.5D 视图系统专项审计报告

- 审计对象：`InkFlow_V1.8.1.html`
- 源码大小：250,367 bytes（Library 原始记录）
- 本次本地读取内容：完整 HTML，24 个内嵌 script
- 审计范围：山水构图、生态坐标、动物/植物/建筑叠加、地形渲染、相机、落墨、生态编辑拾取、视图切换
- 审计类型：静态源码审计 + JavaScript 语法检查
- 不包含：真实浏览器视觉回归、用户截图黑色区域的确定性根因定位、长期性能基准

## 1. 结论

**当前 V1.8.1 不是统一的 2.5D 系统。它由“二维远观水墨画布 + 直接按栅格坐标叠加的生态层 + 独立 WebGL 透视地形视图”拼接而成。**

用户指出的“山水是远观视角，生物却像俯视地图”是源码可以确认的架构问题，不是单纯的美术细节。

当前有两个互不共享完整场景图与相机的渲染入口：

1. `paper`：1200×750 Canvas 2D。`LivingScene.paint()` 绘制固定的远观山水；生态水文、植被、动物、繁殖/营造标记和落墨物理层再按二维栅格位置覆盖其上。
2. `terrain3d`：独立 WebGL Canvas。重新从山脊样条生成高度场，使用透视相机绘制地形、河流、植被、领地和简化动物网格。它不是主水墨画布的 2.5D 延伸，而是另一个独立视图。

因此，单独修动物贴图、加阴影或改落墨笔刷，不能根治问题。必须先统一世界坐标、投影、遮挡和拾取。

## 2. 当前架构还原

```text
生态模拟 EcoSim (w×h 栅格)
  ├─ 水文 / 土壤 / 高程 / 植被
  ├─ 动物 x,y / 领地 / 记忆 / 营造
  │
  ├─ paper Canvas 2D
  │    ├─ LivingScene：远景/前景山水、云雾、瀑布、树木
  │    ├─ EcoSim.paint：水、侵蚀、植被
  │    ├─ EcoCoevolution.paint：花朵/种子等
  │    ├─ InkFauna2D.paint：动物图元
  │    ├─ InkBuild / InkLife：巢穴、小径、栖息地标记
  │    └─ InkFlow：独立 240×150 墨水物理层，最后整幅叠加
  │
  └─ terrain3d WebGL Canvas（切换后替代 paper）
       ├─ Terrain3D._buildTerrain：另行重建高度场
       ├─ _buildRivers / _buildPlants
       ├─ _buildSocial：动物与领地网格
       └─ perspective + lookAt：可旋转透视相机
```

## 3. 关键审计发现

### F-01 / 严重：两个渲染世界没有统一场景图

**证据位置**
- `16_terrain3d_renderer_and_app_input.js`：`paint()`、`setTerrainMode()`、`Terrain3D.render()`
- `02_living_scene_2d_composition.js`：`LivingScene.paint()`
- `ui_relevant_dom.html`：`paper` 与 `terrain3d` 是两个独立 canvas

`setTerrainMode()` 通过隐藏一个 canvas、显示另一个 canvas 来切换。主水墨画和 WebGL 地形不是同一套场景的两种相机表现。

**后果**
- 切换视图时，山体形状、材质、空间组织会改变。
- 主画布的云雾、瀑布、树木、动物、巢穴、小径与三维视图无法保持完整一致。
- 用户无法在同一视图里同时获得水墨风格和一致的空间生态。

**判定：确认。**

### F-02 / 严重：生态栅格的 y 轴在不同渲染器中含义不一致

**证据位置**
- `03_ecosystem_grid_hydrology_and_2d_paint.js`：`EcoSim._buildTerrain()`、`EcoSim.paint()`
- `15_fauna_2d_overlay.js`：`InkFauna2D.paint()`
- `16_terrain3d_renderer_and_app_input.js`：`Terrain3D._world()`、`_buildTerrain()`

二维渲染直接执行类似 `screenY = gridY × 750 / h` 的映射；而 WebGL `_world()` 把同一个 `gridY` 映射到世界坐标 z（深度轴），把高度场映射到世界 y（垂直轴）。

`Terrain3D._buildTerrain()` 的源码注释也明确写出：它重建的体积地形“Unlike the 2D ecological mask”，即它与二维生态掩膜不是同一几何表达。

**后果**
- 在二维画布上，动物的 y 坐标是屏幕上下位置。
- 在 WebGL 地形上，同一个 y 坐标变成前后深度。
- 两者不是同一个投影下的同一个地点，因而动物、植被和编辑位置无法在两个视图中严格对齐。

**判定：确认，是本次问题的根因之一。**

### F-03 / 严重：动物按平面坐标画在远观山水上，没有地表投影

**证据位置**
- `15_fauna_2d_overlay.js`：`sx=1200/eco.w`、`sy=750/eco.h`，再用 `x=a.x*sx`、`y=a.y*sy` 绘制。
- `16_terrain3d_renderer_and_app_input.js`：二维 `paint()` 的绘制顺序。

二维动物没有读取地形高度，没有按深度改变尺寸，没有与山脊做遮挡，也没有前后层排序。鸟类只通过固定的像素 y 偏移与翅膀曲线表达飞行。

**后果**
- 动物像图标一样贴在整张画布上。
- 地面动物可以出现在山体轮廓、天空或前景不合理的位置。
- 远处动物不会自然缩小，也不会被近处山脊挡住。

**判定：确认。**

### F-04 / 高：二维生态对象都各自做了一遍“栅格→屏幕”的映射

**证据位置**
- `03_ecosystem_grid_hydrology_and_2d_paint.js`：`EcoSim.paint()`
- `07_evolution_stress_and_fire_visuals.js`：火灾绘制
- `11_plant_animal_coevolution_visuals.js`：植物绘制
- `15_fauna_2d_overlay.js`：动物绘制
- `22_life_ui_overlay.js`：栖息地标记
- `23_build_ui_overlay.js`：巢穴和小径绘制

这些模块分别把栅格索引换算成 1200×750 画布位置，没有统一的 `worldToScreen()`。以后只要改相机或透视，就必须逐个修补，极易产生错位。

**判定：确认。**

### F-05 / 高：二维叠加没有深度排序和地形遮挡

**证据位置**
- `16_terrain3d_renderer_and_app_input.js`：主 `paint()` 依次绘制山水、生态层、动物、墨水层。
- `15_fauna_2d_overlay.js`：按物种数组顺序绘制，没有深度排序。
- `03_ecosystem_grid_hydrology_and_2d_paint.js`：植被在山水绘制完成后直接叠加。

**后果**
- 动物和植物总是在对应绘制阶段覆盖前景山体。
- 墨水物理层最后覆盖整个画面，不能附着在山坡表面。
- 视觉上缺少前景遮挡、接触阴影和山体空间层次。

**判定：确认。**

### F-06 / 高：落墨是独立平面，不是地形表面的笔触

**证据位置**
- `00_ink_physics.js`：墨水物理状态保存在独立 `InkFlow(240,150)` 网格。
- `16_terrain3d_renderer_and_app_input.js`：主 `paint()` 最后把 `simCanvas` 拉伸绘制到整张 `paper`。
- `16_terrain3d_renderer_and_app_input.js`：二维画笔 `pos()` 只按 canvas 矩形换算到墨水网格。

**后果**
- 墨迹不会沿山坡、山脊或地表法线改变形状。
- 墨迹始终处于画面最前层，无法被山体遮挡。
- 画笔看起来像在整张截图上盖墨，而不是在一个有空间起伏的世界里落墨。

**判定：确认。**
黑色椭圆的具体来源不能只凭静态源码唯一确定；它可能来自当前墨水状态或其他诊断/生态绘制状态。需要用相同种子、工具和画布状态复现后才能给出单一归因。但“墨水层是平面覆盖层”这一结构问题已确认。

### F-07 / 高：编辑拾取仍是二维线性映射，且工具不能在 WebGL 视图使用

**证据位置**
- `19_ink_forge_operations.js`：`InkForge.apply()` 直接以栅格 x,y 操作 `e.land[i]`、`e.height[i]`。
- `20_forge_pointer_mapping.js`：`point(ev)` 用画布矩形线性映射到 `eco.w/eco.h`。
- `20_forge_pointer_mapping.js`：选工具时若处于 `terrainMode`，调用 `setTerrainMode(false)`。
- `16_terrain3d_renderer_and_app_input.js`：WebGL canvas 的指针事件只用于旋转相机，没有地形拾取。

**后果**
- 用户点到画面上“看起来是山体”的位置，不保证命中同一个生态陆地网格；可能得到“此处不适合该工具”。
- 3D 视图无法直接隆地、削地或在地表落墨。
- 相机一旦采用 2.5D 投影，旧的线性映射必然失效。

**判定：确认。**

### F-08 / 高：三维视图没有迁移全部生态可视化模块

**证据位置**
- `22_life_ui_overlay.js` 和 `23_build_ui_overlay.js`：绘制函数在 `terrainMode` 下直接返回。
- `16_terrain3d_renderer_and_app_input.js`：`Terrain3D` 目前只绘制地形、河流、植被、领地和简化动物。

**缺失表现**
- 生灵记忆/栖息地标记。
- 鸟巢、洞穴和小径。
- 二维共生植物/火灾等专用覆盖层。
- 自由落墨及其材质效果。

**判定：确认。**

### F-09 / 中：现有 WebGL 相机是可旋转透视相机，不是稳定的 2.5D 相机

**证据位置**
- `16_terrain3d_renderer_and_app_input.js`：`perspective()`、`lookAt()`、`Terrain3D._events()`。
- 初始参数：`yaw=.72`、`pitch=.66`、`distance=4.65`；拖动可改变 yaw/pitch，滚轮可改变距离。

**后果**
- 它更接近可绕场景旋转的三维观察器。
- 不能稳定保持用户想要的“远观山水”构图。
- 不能单靠缩小旋转幅度就变成 2.5D；需要明确的固定投影与空间层级设计。

**判定：确认。**

### F-10 / 中：三维动物网格表现和更新频率仍是占位级

**证据位置**
- `16_terrain3d_renderer_and_app_input.js`：`Terrain3D._buildSocial()`、`Terrain3D.update()`。

观察到：
- 动物主要由少量三角形组成。
- 地面动物和飞行动物只使用固定高度 lift 区分。
- 地表高度用最近栅格 `Math.round()` 采样，没有双线性插值。
- 社会网格的重建节流为约 420ms；主渲染约 33ms 一帧。

**后果**
- 地形高度变化时，动物脚底可能出现格点式高度跳变。
- 高速模拟时，动物图元可能明显滞后于模拟状态。
- 鸟类没有独立飞行高度/阴影，地面动物没有足部接地与坡面姿态。

**判定：确认。**

## 4. 对用户截图的判断边界

截图中可以确认：
- 当前使用的是水墨远观构图。
- 工具栏选择了“隆地”。
- 页面提示当前位置不适合该工具。
- 画面中存在一个不符合山水构图的深色椭圆区域。

源码能够解释“工具点击位置与生态栅格可能错位”和“墨迹/生态覆盖层没有地形投影”的结构原因。但静态代码不足以唯一确认该椭圆是哪一个状态数组或绘制模块产生。不能把它武断归因成某一个具体 bug。

## 5. 2.5D 正确架构建议

### 5.1 唯一世界坐标

统一使用：

- `X`：地表横向坐标
- `Z`：地表前后/深度坐标
- `H(X,Z)`：地形高度

生态模拟仍可使用二维网格，但网格明确代表地面 XZ 平面；高度只由地形采样函数提供。禁止某个模块把 gridY 当屏幕 y，另一个模块又把它当世界 z，却没有显式转换。

### 5.2 唯一投影与拾取

建立公共接口：

- `gridToWorld(gx,gz)`：栅格→世界坐标
- `sampleHeight(x,z)`：双线性地形高度采样
- `worldToScreen(world)`：世界→屏幕
- `screenToGround(screen)`：屏幕射线与地表求交，返回世界坐标/网格
- `depthKey(world)`：用于透明对象与精灵排序

所有动物、植物、河流、巢穴、小径、火灾、墨迹和工具必须调用同一组接口。

### 5.3 统一 2.5D 相机

建议采用固定的斜俯视正交/弱透视相机：
- 保留远观山水构图。
- 前后方向有可读的深度差。
- 远景山脉使用低对比度与视差层。
- 前景山体能够遮挡后方动物。
- 不开放任意绕场景旋转，避免构图漂移。

### 5.4 统一渲染顺序

1. 宣纸底色与远景雾层
2. 远山/中景山体
3. 可交互地形表面
4. 贴地水墨纹理与河流
5. 植被、巢穴、洞穴、小径
6. 地面动物与鸟类（按深度排序）
7. 前景遮挡山体与树木
8. UI 与选中反馈

落墨必须成为地形表面的 decal/纹理或沿地表投影的笔触；若保留纯纸面绘画，则应独立成为“纸面绘画模式”，不能混在生态世界中。

## 6. 推荐整改顺序

| 优先级 | 工作 | 验收标准 |
|---|---|---|
| P0 | 定义唯一 XZ+H 世界坐标 | 同一生态格在二维/2.5D/诊断视图中定位一致 |
| P0 | 建立统一投影和屏幕拾取 | 点击动物/地表后命中同一世界坐标；投影往返误差受控 |
| P1 | 把动物和植物迁移到统一投影 | 贴地、远近尺度、山体遮挡正确 |
| P1 | 把巢穴、小径、领地、火灾等全部迁移 | 不因视图切换而消失或错位 |
| P1 | 把落墨改为地形表面投影 | 笔触跟随坡面、可被前景遮挡 |
| P2 | 固定 2.5D 相机和远中近景层次 | 保留国画远观构图，镜头稳定 |
| P2 | 移除双渲染管线的重复实现 | 仅保留一个场景图和一个坐标变换体系 |

## 7. 审计测试结果

- 内嵌 JavaScript：24/24 通过 `node --check` 语法检查。
- 源码静态检索：未发现 `orthographic`、`worldToScreen`、`screenToWorld`、`unproject`、`raycast`、`inverseMVP`、`depthSort` 等统一投影/拾取/深度排序接口。
- 源码静态确认：二维绘制存在多处直接 grid→canvas 映射；WebGL 使用 `perspective + lookAt`。
- 未执行：真实浏览器截图回归、交互拾取误差测试、不同设备性能测试。

**最终审计结论：当前问题是渲染架构与坐标语义不统一。应先重构视图底座，再继续开发动物行为和生态内容。**
